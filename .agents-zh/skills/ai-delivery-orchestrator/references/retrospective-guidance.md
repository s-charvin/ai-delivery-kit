# 复盘指导

需求级 `retrospective.md` 是已知交付问题的唯一持续维护台账。UI、逻辑、迁移、架构、集成、测试及工具问题一视同仁，遇到问题就收集，不按类别设置收集优先级。正常编辑和正常执行不自动算问题。不增加阶段、角色、产品规格或审批链。

## 需求级收录与项目复用分开

用户明确指出的所有问题必须进入复盘，包括一行或机械修正、已经修复、暂不解决、尚未复现、根因未知以及仅本需求适用的问题。保留用户描述、来源、实际观察和当前处置状态；AI、评审、验证和运行发现的问题也须记录。测试全绿不能排除用户观察。

`importance`、`confidence`、`reuse_scope`、`knowledge_type` 和 `index_decision` 描述知识属性及项目索引资格，不能成为需求级收录门槛。不为收录局部问题伪造已确认根因、高重要性或通用价值；没有通用教训时可简短记录。确认属于误解、产品决定变化或已无法复现的反馈，仍保留原反馈、判断及依据，不静默删除，也不把所有决定都标成缺陷。

## 收集、归并与逐项核对

1. 收到用户纠正，或在实施、评审、验证中遇到问题后，**下一次尝试前**记录现象、来源、当前假设和已有证据。未定因保留未知。先完整保存用户原文到所属需求提示词组，见 [framework-adaptation.md](framework-adaptation.md)。
2. 按触发条件、根因和最小修正路径判断归属。同机制更新原RET，保留每个具体反馈及实质尝试；相似关键词不能单独支持合并。独立机制才新建稳定 `RET-###`，并融入分类和问题地图。
3. 批次收尾时，逐项核对所有用户问题及其他已知发现是否有具体RET案例和处置状态。复用 `verification.md` 的发现记录及提示词输入锚点，补上RET引用，不另建覆盖账本。只有“已有类似RET”但没有该问题的具体观察及结果，不算覆盖。
4. 归档前从原始记录反查，遗漏直接整合正文，再更新唯一审阅标记。复用已明确归属和有效证据，不反复扫描全部历史日志。

完整指全部**已知**问题可定位，尤其用户明确提出的每个问题，不代表已发现所有潜在缺陷。RET引用不自动关闭原始反馈。区分待复现、偏差已证但根因未证、已修未运行、局部验证与正式验收；`confidence=confirmed` 只针对有证据支持的结论，不代表所有UI状态已验收。保留STOP、豁免、已撤回假设及未验范围。

## 统一正文，严格禁止补丁式复盘

`retrospective.md` 必须始终是一份统一、连贯的需求复盘。所有新增发现融入统一分类及对应条目。**严格禁止按修订批次追加正文**，如“2026-11-03补审”“本轮新增”“追加复盘”，或在文末堆积游离补充。不得创建UI专用复盘、阶段副本、补充复盘或第二份问题清单；修改说明交给Git历史。

同一机制完整详情只维护一份；分类和问题地图只做路由，不复制失败叙述。保留稳定ID、锚点、失败尝试、证据和撤回依据，后续结果归回所属问题。真实失败日期、来源版本变化及验证日期可保留在问题条目内；来源评审、决定、运行记录按时间留存是允许的。不得把此规则实现成禁止所有日期。

## 条目结构

使用[复盘模板](../templates/retrospective-template.md)，保持“分类路由→带标记v2问题地图→稳定RET详情”的总分结构。地图每行使用既有五个资格字段，链接自己的详情标题或显式稳定锚点。已有有效锚点继续保留；新条目可用 `ret-001` 显式锚点避免标题变化影响引用。不增加必填机器元数据或第二种表格协议。

详情保留具体反馈／来源及逐项状态，场景、预期／实际和最短复现，根因及证据置信度，实质AI尝试及为何看似合理却失败，修正、实际验证及未覆盖范围。局部或未定因问题可紧凑记录，诚实写未知／未运行／不泛化，不强凑教训或虚构失败测试。确有复用依据时给出适用条件、最小判别、最小修正、最窄验证、停止条件和已否定路径；“以后更仔细”“加强测试”不能代替判别方法。

更新后随正常进度简短告知RET编号、实质变化与路径，不为每次记录另设打断。

## UI专项分析视角（适用时）

适用于 `figma`、`runtime-baseline`、`existing` 等所有UI交付，不扩大原有模式门禁；无UI任务不强加视觉记录。按需调查，不要求每条填满所有维度，也不按维度配额制造问题。

| 视角 | 最小判别问题 |
|---|---|
| 来源及适用范围 | 页面、完整父节点、主题、状态、变量Collection及最新用户决定是否对应？来源到底能证明什么？ |
| 控件、资源与文字 | 为何选择此真实控件／素材？核对字重、字号、行框、fontPadding、渐变、间距、圆角、图标transform及画布与槽位。 |
| 布局及完整合成 | hug/fill/fixed、锚点、裁剪、底层、蒙版及生产宿主组合是否正确？局部正确不能证明父合成。 |
| 运行状态与动效 | 最后哪个赋值生效？主题／背景／IME／面板／发送／失败／引用／loading过程是否回到旧UI？静态loading图不能证明动效。 |
| 正式接线及回归 | 真实入口是否启用新UI？共享消费者、重绑、返回、首次绘制在已证范围内是否正确？ |

串起“可见偏差→权威来源→AI错误判断或遗漏→修正→实际验证与剩余边界”，保留具体错误尝试及其看似合理的理由。不将项目特定token数值、字段或产品决定升级为通用规则。

## 渐进式读取与项目索引

项目索引 `.ai-delivery/retrospectives/index.md` 只收录明确符合复用资格的已归档行：`knowledge_type=reusable`、`reuse_scope=project` 或 `domain`、`index_decision=include`、`confidence=confirmed`、`importance=high` 或 `critical`。缺失或无效资格不可索引。索引只保触发、场景、最小路径、状态、归档日期及精确详情链接，不复制完整根因或失败叙述。

### 旧台账归档前升级

若使用 `problem-index:v1` 或旧六列表格，AI先读完整详情，原位升级为v2，保留ID、标题、锚点、证据和结论。只从已有证据分类，不能看标题推断复用或重要性；无法确认时使用保守的 `index_decision=exclude`、`confidence=unverified`，全文仍保留。归档脚本拒绝旧格式，避免静默丢失或过度索引。

创建或恢复需求时：

1. 读取紧凑项目索引及当前需求问题地图（如存在）。
2. 按当前可见触发和适用条件筛选。
3. 只加载匹配的历史问题章节，先执行最小判别再考虑修正。

新现象出现时再检索；关键词相似不够。历史经验不能覆盖当前证据、架构约束、产品要求或未确认外部事实。

## 归档行为与能力边界

即使没有已知问题，也必须有台账。保留唯一 `<!-- ai-delivery-retrospective:reviewed-at:<ISO-8601> -->`，完成原始发现到RET的最终核对后更新，日历日期须与归档一致。真正无问题的空台账有效，不能用空台账绕过已知问题。

归档不会生成、重写或语义审计台账。脚本检查审阅标记及客观地图／详情结构，再仅将明确符合资格的行幂等替换到项目索引。结构检查发现重复标记／ID、缺失或孤立详情、无效锚点和可识别的修订批次标题，提供文件／行号。它不能证明所有反馈已收录或所有同机制重复已合并；这些由原始发现核对与行为评估承担。脚本通过后，未识别的补丁式散文仍可能需要审查。

临时决定、仅需求适用、根因未证和机械修正保留在台账；不合资格行不写索引。需求旁的台账是完整历史源，不生成归档副本。归档后台账及其索引条目只读；后续发现进入新需求，可链接旧问题。
