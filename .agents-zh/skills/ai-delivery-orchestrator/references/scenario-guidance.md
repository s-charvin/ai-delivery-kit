# 场景指导

这是一个可选、按触发条件使用的变更分析指导目录。它补充宿主工作流的常规交付规则，
不定义或替代宿主工作流。只有某个场景自身的触发条件与需求匹配时才选择它；没有匹配场景时，
继续使用常规需求与评审规则，不要自行发明场景。“可选”表示该目录只在已知变更情境适用时
作为参考，不是必做的交付活动。
场景指导只是分析视角，不是新的工作项或生命周期规则：选择它不会自动增加工作流步骤、
门槛、路由、控制状态或审批要求。
场景 ID 描述的是变更情境，而不是交付阶段或实现顺序；不能从 ID 推断新的阶段或执行次序。

## 使用方式

1. 对照目录中的触发条件，只选择与需求匹配的场景 ID。
2. 需求可以组合场景，但必须分别写清触发条件和边界。
3. 每个场景只应用到需求影响的表面，并停在场景声明的边界内。
4. 将产生的决策和证据写入宿主工作流已有记录或当前动作报告；不得为场景指导新增阶段、
   产物类型或跨动作维护义务。

## 建议的决策记录

当选中的场景产生实质决策时，建议在宿主工作流已有的决策、备注或当前动作报告中使用以下
紧凑结构。标题可以本地化；不要仅为本指导创建新的生命周期产物：

- 选中的场景 ID 以及触发它的需求证据；
- 受影响表面、决策、边界、责任人和明确的非目标；
- 选中场景要求的正向和负向验收证据；
- 未决事实、决策责任人和停止工作的边界。

这份备注不是对宿主工作流既有记录的替代，也不要求后续产物维护链接或内容哈希。若宿主在
当前动作没有持久记录，就在当前动作输出中报告决策并继续；不要创建平行工作流模型。

## 场景目录

| ID | 触发条件 | 核心问题 |
|----|----------|----------|
| `existing-function-semantic-replacement` | 重构、重新设计或重新定义已有能力的业务含义 | 旧语义哪些保留、适配、迁移或退役？ |

未来新增场景建议保持同样的基础结构：触发条件、决策模型、受影响表面或适用性、边界、
证据要求和明确的非目标；场景专属子节可以按需增加。每个条目必须有稳定且唯一的场景 ID，并在每种维护中的语言
副本中有对应区块。优先新增条目；改变既有 ID 的含义时必须记录版本或迁移说明。

## `existing-function-semantic-replacement`

### 触发条件

已有能力正在被重构、重新设计或赋予新的业务含义，且至少一个可观察边界
可能发生变化。

没有既有行为的全新能力，或已证明外部可观察契约与边界均未改变的纯机械修改，不应选择本场景。

### 决策模型

选择最小且真实的分类：

- `preserve`：可以更换实现，但外部行为保持不变。
- `extend`：旧行为仍然有效，需求在其上增加行为。
- `compatible_replacement`：实现和内部模型改变，但外部契约按意图保持兼容。
- `breaking_replacement`：旧业务含义、流程或契约被有意替换。
- `unknown`（未知）：需求没有说明旧行为是否继续存在。
- `mixed`（混合）：不同表面明确具有不同关系；仍需为每个表面记录自己的分类和边界。

不要把 `unknown` 默认为兼容。`breaking_replacement` 必须有明确的退役边界；
兼容替换必须有定义清楚的迁移或兼容边界。

能力级别可以保留一个汇总分类，但清单中的每个表面仍需分别记录新旧关系和交付动作。
因此，同一次替换可以保留纯工具、适配状态映射并退役旧入口，而不能据此推断整个能力仍然兼容。

### 影响清单

记录简洁的新旧行为差异和旧行为清单。适用时至少清点：

- 入口、路由、深链、命令和事件重放；
- 状态、转移、恢复、重试和并发行为；
- 持久化、缓存、快照、凭证和失效规则；
- 协议适配器、请求载荷、响应映射和错误处理；
- 埋点、通知、副作用、功能开关和后台工作；
- 交互或含义可能改变的可见界面。

为每个适用表面附上基线证据：需求或设计来源、已有测试或运行观察。已有测试和生成引用
只能证明旧实现，不能自动作为目标契约的证据。

对每一项清单使用复用矩阵，分开记录以下字段：

- **relationship**：`preserve`、`extend`、`compatible_replacement`、
  `breaking_replacement` 或 `unknown`；
- **action**：`preserve`、`adapt`、`migrate`、`retire` 或 `unknown`；
- 旧契约、目标契约、责任人，以及正向和负向验收证据。

对于持久化表面，还要记录旧数据是读取、写入、迁移、清理还是忽略；版本或命名空间边界；
适用的身份隔离范围；以及重启、崩溃、回滚或部分发布后的行为。不适用的字段必须写明理由，
不能静默省略。

将这些事实写入宿主工作流已有记录或当前动作报告；不要在派生产物中复制互相冲突的版本。

### 边界

应做：

- 在检查候选代码前先建立旧的可观察契约；
- 逐项验证复用表面是否符合目标契约并标明责任人；
- 如果受影响表面属于其他责任人，记录交接或依赖，并将实现限制在已授权边界内；
- 涉及持久化、鉴权或外部副作用时，定义迁移、发布、回滚和失效边界；
- 破坏性替换时退役或隔离旧路径，并测试这些路径已不可达；
- 将场景决策和证据保留在宿主已有记录或当前动作报告中。

不应做：

- 仅为保持编译而保留旧行为；
- 把文件位置、命名、共享缓存键或已有页面当作语义兼容证据；
- 在目标契约或明确批准的兼容边界之外添加回退映射、载荷字段、持久化或副作用；
- 因为选择了本指导就修改宿主工作流的路由或生命周期，或扩大需求范围；
- 因为选择了本指导就对需求无关的表面开展全仓库旧行为审计；
- 仅为让场景看起来完整就实现其他责任人的表面；应记录依赖并在边界处停止；
- 猜测缺失的协议、鉴权、迁移或责任归属事实。

#### 复用与退役

- 可以复用已验证契约与目标一致的基础设施、纯工具、数据源和组件。
- 结构复用不等于语义复用。不要根据代码位置或命名推断兼容。已有页面、共享缓存键或熟悉的适配器也不能作为兼容证据。
- 不要仅为了让旧调用方继续编译，就保留旧状态映射、回退分支、载荷字段、缓存读取、入口或副作用。
- 对于破坏性替换，旧行为必须退役、隔离或明确迁移；隐式桥接属于缺陷。
- 对于兼容替换，定义兼容边界，并在该边界测试旧表示和新表示。
- 如果缺少协议、鉴权、迁移或责任归属等必要事实，只在宿主工作流既有记法中标记依赖该事实的
  决策或任务正在等待，并询问缺失事实。独立工作可以继续；不要猜测 endpoint 名称、令牌字段、
  过期时间、错误码或等价协议细节。

### 证据

验收既要覆盖目标行为，也要覆盖不应再可达的旧行为。正向和负向验收应按适用性
覆盖入口、旧快照、缓存恢复、事件重放、重试、并发调用和副作用边界。新鲜上下文评审
必须追问仍可触达哪些旧路径，以及每一项保留的复用是否有语义兼容证据。
每个退役或隔离表面都要写明退役边界并附上该边界的负向证据；不要声称删除了范围外
的旧行为。适用时还要检查重复副作用，以及过时测试或生成引用。

组合多个场景时，指定一个主场景，其余标为辅助场景，并按表面合并分析。若决策冲突，只将
冲突表面归类为 `unknown`，停在最窄边界并询问责任人；任何场景都不能默认胜出。

### 非目标

- 本场景不重设计周边交付工作流，也不创建新的生命周期、审批或控制模型。
- 本场景不要求审计、迁移或兼容与需求无关的旧表面。
- 本场景不替产品、协议、鉴权、迁移或责任归属的所有者决定缺失事实；这些事实必须显式决策。

## 扩展目录

新增场景时保持可选且与技术无关。定义稳定、唯一的 kebab-case ID、触发条件、分类或决策
模型、受影响表面或适用性、边界、验收证据和非目标；只有场景触发条件确实需要时才增加
专属子节。将同一 ID 加入目录，并在每种维护中的语言副本中增加对应区块；校验唯一性和语言对齐。
不要在目录中写入项目名、框架假设、宿主专属路由、
新的工作流控制 token、特定产品或领域字段名、示例载荷字段，或隐藏的兼容默认值。
