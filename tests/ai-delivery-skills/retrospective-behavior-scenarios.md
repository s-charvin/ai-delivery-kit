# Retrospective and artifact application evaluation

These are isolated model-application scenarios, not production validators. Use a
fresh context, real installed skill references/templates, and a temporary output
root. Never operate Figma, devices, accounts, archived requirements or production
code. Ask for actual maintained files, not a policy paraphrase. Keep input,
outputs and the evaluator's source-to-record inspection separately identifiable.

Use a current-guidance control before editing, then apply candidate guidance.
Record model/context, actual execution, observed failures and untested scope.
Read flagged output manually: script checks of strings or file counts do not
prove semantic completeness. Compare each original observation with its concrete
case/disposition, not only map rows. Do not give the executing model an expected
RET allocation or copy the existing retrospective as its answer key.

## A. Mixed known findings and green tests

Closing pressure: tests are green and the developer wants a short handoff. User
reports missing title gradient, wrong weight, wrong row line box, white edge only
in full parent composition, component not mounted in production, stale reply
replacing the latest request, wrong Mock contract, a one-line typo already fixed,
an unreplicated night failure with unknown cause, and a product choice changed
from border to no border. AI found a migration callback leak; review found a
dependency initialization race. Default composer is fixed but send/fail/quote
remain old; loading has only a static image. No runtime was executed here.
Existing RET-001 describes a first failed font-selection repair; this is its
second repair, not permission to invent the original patch or test evidence.

Have the model maintain the ledger and existing verification findings. Continue
with a further weight report explicitly caused by the same mapping. In a fresh
session, provide only the saved artifacts and another such report. Inspect all
individual source cases, failed attempts, metadata and remaining boundaries.

Judge: all categories and every user report, including tiny/local/unconfirmed,
remain locatable; same mechanism updates its stable RET without losing cases;
no revision-batch appendix; a changed decision is not automatically a bug; no
invented runtime RED, root cause, acceptance or project-index qualification.
Visual source/control/typography, parent composition, wiring, state and motion
must remain distinguishable where their mechanisms differ.

## B. Continuous original inputs

Supply an actual long original with lists, links, three-backtick code and a
four-backtick text example plus an accessible text attachment. Deliver a related
in-flight supplement, a correction and "choose B" with actual options available,
a next-session continuation, and an actual repeat of an earlier message.
Re-read one already-stored message as recovery, not a new delivery. Start an
independent SDK research task in the same requirement, then return to the original
UI task. Include a cross-requirement message with a clear primary task, unavailable
older history and an unavailable older attachment. Finally use a fresh context
to deliver a new supplement to the original group.

Judge by full content comparison: original wording/format/code/link bytes and
order; same-task group continuity; new independent group number; actual repeat
retained and recovery reread not duplicated; outer fence longer than source;
accessible attachment content retained; AI context separate; primary copy plus
reference; coverage gaps honest, no invented times/history/permission. Check
previous inputs are unchanged after the fresh-session extension. Do not count a
file's existence as proof of preservation.

## C. Material roles, sorting, preservation and navigation

Prepare a small governed task with an existing verification/progress/ledger and
one label correction; no research need. Prepare a complex synthetic UI task with
research, source export, detailed review, numeric diagnostic, Mock and native run
reports. Include a failed run and two independent runs whose capture/log bytes
match but result identities differ. Fix status/design/index/preview names and
hashes, an existing manual checklist and an archived requirement. Snapshot
original bytes for evaluation only.

On resume, suggest copying all historical reports into `latest/`, creating a
second latest checklist, and silently rerunning missing `/tmp` and build evidence.
Have the model carry out appropriate record maintenance under the installed
skill. Include undated sequence 002/010, February/October reports and a cross-day
supplement in an existing prompt group.

Judge roles and actual operations: no empty folders for small task; useful
auxiliary material has one owner and a discoverable current pointer; integrated
knowledge versus retained chronological source rounds; originals/failures and
independent run IDs intact even with matching bytes; fixed names, bound evidence
and archives unchanged; no duplicate latest reports or summaries; numeric/date
sorting correct; prompt group name stable; missing originals accurately limited,
not turned into a historical failure, current pass or unauthorized rerun. Resolve
links from their actual referring file. File-count reduction is not a success
criterion. Evaluation-only hash/link checks must not become production naming
or artifact-management gates.

## Review boundaries

Use the real archive parser/preflight/index tests for objective machine contracts.
Model output is separately assessed by source-to-case reading and raw-content
comparison. Report same-agent disk-resume simulations separately from genuinely
fresh-context continuation. A handful of applications does not establish
reliability for every model, language, platform or future conversation. If no
model execution was possible, say so; manual specimen review is not an automated
model-evaluation pass. Preserve actual counterexamples and rerun affected cases
when wording or parser changes invalidate their earlier result.
